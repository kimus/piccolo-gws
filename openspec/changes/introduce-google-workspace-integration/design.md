## Context

Piccolo will treat integrations as external packages installed into a custom gateway image. It discovers an installed integration by running its binary's `describe --json`, and it runs provider-specific setup inside a temporary container created from that image. Therefore `piccolo-gws` must own its installation metadata, setup flow, Google auth, config/state layout, and MCP server behavior.

The integration should not require the model to discover arbitrary `gws` or Google API syntax. Instead, it should expose a deliberately small, read-only MCP surface at first.

## Goals / Non-Goals

**Goals:**

- Provide a `piccolo-gws` binary installable from `github:kimus/piccolo-gws` as a Nix flake package.
- Implement `piccolo-gws describe --json` using the `piccolo.integration.v1` descriptor contract.
- Implement `piccolo-gws setup` to perform Google-specific setup, auth guidance, state initialization, and PicoClaw `config.json` patching.
- Implement `piccolo-gws mcp` as a stdio MCP server.
- Expose initial read-only tools for Gmail, Calendar, and Drive.
- Store integration state under `/root/.picoclaw/integrations/google` when running in Piccolo containers.
- Use `gws` or the Rust `google-workspace` crate internally while keeping the MCP contract stable.

**Non-Goals:**

- Implement Piccolo's image build or lifecycle commands in this repo.
- Expose raw arbitrary Google API or raw `gws` command execution as MCP tools.
- Support write/send/delete operations in the first version.
- Run as a sidecar HTTP MCP server in the first version.
- Store secrets in Piccolo-owned `piccolo.yaml`.

## Decisions

### Stable MCP surface over raw CLI discovery

The MCP tools are semantic operations such as Gmail search/read, calendar list/read, and Drive search/read. The model never receives a general-purpose `gws` command runner. This keeps behavior predictable and gives the integration control over pagination, error handling, and safety boundaries.

### Setup owns PicoClaw config patching

`piccolo-gws setup` updates `/root/.picoclaw/config.json` to enable `tools.mcp` and register the Google Workspace MCP server using the installed command:

```json
{
  "enabled": true,
  "type": "stdio",
  "command": "piccolo-gws",
  "args": ["mcp", "--config-dir", "/root/.picoclaw/integrations/google", "--read-only"]
}
```

Piccolo core does not construct this provider-specific config.

### Descriptor is generated by the binary

`piccolo-gws describe --json` returns a versioned descriptor that tells Piccolo how to run setup. This avoids a separate metadata file and makes the installed binary the source of truth.

### Read-only by default

The first version runs in read-only mode. Write operations such as sending mail, editing Drive files, and creating calendar events are excluded until an explicit confirmation model is designed.

### Backend can evolve under a stable contract

The initial implementation may shell out to `gws` or use a Rust Google Workspace crate directly. That is an internal implementation detail as long as `piccolo-gws` commands and MCP tool schemas remain stable.

## Risks / Trade-offs

- **Workspace data is prompt-injection prone** → Tool descriptions and setup guidance must warn that email/docs/calendar content is untrusted input.
- **OAuth setup is brittle in containers** → Descriptor-declared setup ports and container-local config paths must be explicit and testable.
- **Raw `gws` output drift** → Normalize all backend responses before returning MCP results.
- **Nix flake dependency complexity** → Keep the flake package responsible for all runtime dependencies, including `gws` if shelling out.
- **Config patching can damage user-owned config** → Setup must merge-patch conservatively, preserve unknown keys, back up before writes, and print a diff/confirmation for changes.
